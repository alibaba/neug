# Explicit Transactions

An explicit transaction groups several queries into one unit of work. Begin the
transaction, run its queries, then commit all changes together or roll them all
back.

Both Embedded (AP) and Service (TP) mode provide the same explicit-transaction
guarantees and use the same begin, commit, and rollback flow. Their transaction
models differ, as do the owning client object and network-related failure
conditions.

## Run an explicit transaction

### Embedded mode

In Embedded mode, a `Connection` owns the transaction.

<Tabs items={['Python', 'Node.js', 'C++']}>

```python
try:

```

### Group persistent `COPY FROM` statements

An Embedded read-write transaction can group multiple persistent
`COPY ... FROM` statements. They share one private COW view, so a later COPY can
use vertices loaded by an earlier COPY and reads on the same `Connection` see
the accumulated data. Individual COPY statements do not publish checkpoints;
`commit()` publishes all COPY changes with one checkpoint, while `rollback()`
discards them all.

Reads may be interleaved with COPY statements. Persistent COPY currently cannot
be mixed with ordinary DML or DDL writes in the same transaction, in either
order. If you define the target schema with separate DDL statements, execute
them before beginning the transaction. COPY may also infer and create its own
target schema inside the transaction; that schema and its imported data are
committed or rolled back together. See
[Import without a predefined schema](../data_io/import_data.md) for usage.
A rejected mixed write makes the transaction rollback-only.

```python
# Create the target schema outside the COPY transaction.
conn.execute("CREATE NODE TABLE Person(id INT64, name STRING, PRIMARY KEY(id))")

conn.begin_transaction()
try:
    conn.execute("COPY Person FROM 'person_0.csv' (HEADER=true, DELIMITER=',')")
    conn.execute("COPY Person FROM 'person_1.csv' (HEADER=true, DELIMITER=',')")
    conn.commit()  # Publish both imports with one checkpoint.
except Exception:
    conn.rollback()
    raise
```

A successful COPY makes its data available inside the transaction. The import
is committed only after `commit()` succeeds. `EXPLAIN` can inspect write plans
without changing data or ending the transaction. `PROFILE` executes its query,
so the same restrictions as ordinary execution apply.

Choose transaction size according to available memory and retry cost. Private
changes remain in the workspace until the transaction ends, and a failed batch must
be retried in full. For example, loading vertices in one transaction and edges
in another reduces checkpoint frequency while keeping separate retry
boundaries. Fewer checkpoints do not guarantee lower peak memory; measure both
the COPY and commit phases when comparing batch sizes.

Include `begin_transaction()` and `commit()` in end-to-end load timing. Summing
only individual COPY durations omits the final checkpoint cost. Report COPY
execution time, commit time, and peak memory through commit separately.

### Service mode

In Service mode, a `Session` owns at most one transaction at a time.

```python
    session.begin_transaction()
```

## Shared behavior

Explicit transactions follow the same rules in both deployment modes:

- Only one explicit transaction may be active on a `Connection` or `Session`.
  Nested transactions are not supported.
- A read-only transaction keeps a consistent read view and rejects writes.
- A read-write transaction sees its own successful writes.
- Changes become visible to other transactions only after commit.
- Rollback discards all changes made by the transaction.
- Savepoints and partial rollback are not supported.
- Do not issue concurrent requests through the same `Connection` or `Session`.

## Statements that cannot run in an explicit transaction

The following statements must not be issued while an explicit transaction is
active:

| Statement class | Examples |
|-----------------|----------|
| File export, temporary loading, and batch sources | `LOAD FROM`, `COPY TEMP`, `COPY TO` |
| Database maintenance | `CHECKPOINT` |
| Extension management | `INSTALL`, `LOAD`, `UNINSTALL` |
| Mutating procedure calls | A `CALL` such as `project_graph` or `drop_projected_graph` that changes state |
| Cypher transaction control | `BEGIN`, `COMMIT`, `ROLLBACK` submitted as query text |

Read-only procedure calls are allowed.

There is one important deployment-mode distinction:

- **Embedded mode:** persistent `COPY FROM` is supported in read-write
  transactions under the restrictions above. Other file and bulk statements
  are auto-commit only.
- **Service mode:** `LOAD FROM` and all `COPY` statements are unsupported,
  whether or not an explicit transaction is active. This is a
  [file I/O restriction of Service mode](../data_io/index.md),
  not an explicit-transaction restriction.

## Failure and rollback-only state

If a statement reaches NeuG and fails, its explicit transaction becomes
**rollback-only**. The transaction cannot commit; call rollback before issuing
another query or beginning another transaction.

This includes syntax, semantic-analysis, compilation, and execution errors,
writes attempted in a read-only transaction, and statements rejected by the
rules above.

A validation error raised by the client before it sends the query does not
change the transaction. For example, Python raises `ValueError` for an invalid
`access_mode` and leaves the transaction usable.

For embedded COPY transactions, a checkpoint preparation failure that returns
an error leaves the connection rollback-only. Once checkpoint processing starts
consuming storage buffers, an unrecoverable error terminates the process to
prevent further access to potentially invalid in-memory storage. This existing
checkpoint limitation also applies to explicit COPY commit: it cannot always
return an exception that the application can handle with `rollback()`. After
reopening the database, inspect recovered data before deciding whether to retry
a commit whose outcome was not observed.

## Client lifecycle differences

The commit and rollback guarantees are shared, but local and network clients
have different lifecycle and failure conditions.

### Embedded clients

- The transaction remains active until the application commits, rolls back, or
  closes its `Connection`.
- There is no transaction timeout.
- Closing the connection attempts to roll back an unfinished transaction.

### Service clients

- Closing a `Session` attempts to roll back its unfinished transaction.
- The server may expire an abandoned transaction. The next request reports the
  expiry, after which the client clears its local transaction handle.
- After server shutdown or a network failure, local client state may be stale.
  Close the session and create a new one.
- If the network fails during commit or rollback, the final outcome may be
  unknown. The driver does not retry because replaying the request could apply
  it twice.

## Recommended pattern

Always end a transaction on both the success and failure paths:

```python
session.begin_transaction()
try:
    session.execute("CREATE (:Person {name: 'Alice'})", access_mode="insert")
    session.commit()
except Exception:
    session.rollback()
    raise
```

Keep explicit transactions short, and use auto-commit when statements do not
need to commit together.
