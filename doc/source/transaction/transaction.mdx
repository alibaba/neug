# Transaction Management

NeuG provides the same transaction guarantees in both deployment modes:
**Embedded mode** for in-process analytical workloads (AP) and **Service mode**
for concurrent transactional workloads (TP). The two modes use different
transaction models to provide those guarantees.

At the application level, the following guarantees and basic usage rules are
shared:

- every query runs in a transaction;
- auto-commit is the default;
- several queries can be grouped in an explicit transaction;
- a successful commit is atomic and isolated from other transactions;
- committed changes in a persistent database survive restart.

The main application-facing capability difference is file I/O: `LOAD FROM` and
every `COPY` statement are available only in Embedded mode. Service mode does
not support these statements.

## What ACID means in NeuG

Both deployment modes provide the same user-visible ACID guarantees:

| Guarantee | Behavior |
|-----------|----------|
| **Atomicity** | A transaction either commits all of its changes or publishes none of them. |
| **Consistency** | Schema constraints, primary-key uniqueness, and edge referential integrity are checked before changes become visible. |
| **Isolation** | Transactions observe a consistent database view; concurrent execution does not expose partial changes. |
| **Durability** | Once a transaction commits in a persistent database, NeuG can recover it after restart. In-memory databases are not durable. |

The concurrency and persistence mechanisms differ between AP and TP, but
applications do not need to depend on them. See
[Transaction Model](transaction_model.md) for details.

## Choose a deployment mode

Choose the mode based on how the application connects and whether it needs file
or bulk operations:

| | Embedded Mode (AP) | Service Mode (TP) |
|---|--------------------|-------------------|
| **Typical use** | Analytics, ETL, local tools, batch processing | Interactive applications and network services |
| **Connection** | In-process `Connection` | Network `Session` |
| **Clients** | C++, Python, Node.js | Python, Java |
| **Regular Cypher** | Read, insert, update, delete, schema and index operations | The same |
| **File and bulk statements** | Supports `LOAD FROM`, `COPY FROM`, `COPY TEMP`, and `COPY TO` | Not supported |
| **Explicit transactions** | Supported | Supported |

The same commit and rollback semantics apply to regular Cypher queries in both
modes. Moving an application between modes generally changes how it connects,
not how it commits and rolls back regular work.

## Run transactions

### Auto-commit is the default

Every `execute()` or `Query()` call is its own transaction unless an explicit
transaction is active:

```python
conn.execute("CREATE (p:Person {name: 'Alice'})")  # committed
conn.execute("CREATE (p:Person {name: 'Bob'})")    # committed separately
```

If a statement fails, that auto-commit transaction is rolled back and none of
its partial changes become visible.

Auto-commit is the simplest choice when statements do not have to succeed or
fail as a group.

### Group related queries explicitly

Use an explicit transaction when several statements must commit together:

```python
conn.begin_transaction()
try:
    conn.execute("CREATE (:Person {name: 'Alice'})", access_mode="insert")
    conn.execute("CREATE (:Person {name: 'Bob'})", access_mode="insert")
    conn.commit()
except Exception:
    conn.rollback()
    raise
```

A read-only explicit transaction rejects writes. A read-write transaction sees
its own successful writes and makes them visible to other transactions only
after commit.

For client-specific APIs, supported clients, rejected statements, and
rollback-only behavior, see
[Explicit Transactions](explicit_transactions.mdx).

## Access modes

The optional `access_mode` tells NeuG what kind of operation a query performs:

| Mode | Alias | Use for |
|------|-------|---------|
| `read` | `r` | Queries that do not modify data |
| `insert` | `i` | Creating new nodes and edges |
| `update` | `u` | Updates, deletes, and `MERGE` |
| `schema` | `s` | Creating or changing node and edge tables |

If `access_mode` is omitted, NeuG infers it from the query. An explicitly
specified mode that does not permit the query returns an error.

For Service mode, specifying the narrowest correct mode helps NeuG schedule
concurrent requests efficiently. In Embedded mode, inference is usually
sufficient unless an application wants to validate its intent explicitly.

`CHECKPOINT` is an administrative statement. It runs in auto-commit with
`update` mode and is rejected inside an explicit transaction. See
[Checkpoints](checkpoint.md).

## File I/O and bulk loading

All file-oriented statements are **Embedded-mode only**:

- `LOAD FROM`
- `COPY ... FROM`
- `COPY TEMP`
- `COPY ... TO`

Service mode rejects these statements, whether or not an explicit transaction
is active. Use Embedded mode to prepare or import data, then open the resulting
persistent database in Service mode for online workloads.

In Embedded mode:

- file statements run in auto-commit and cannot be placed inside an explicit
  transaction;
- a persistent `COPY ... FROM` is all-or-nothing and reports success only after
  NeuG has published a checkpoint containing the imported data;
- `COPY TEMP` is scoped to the connection and is lost when the connection or
  database closes;
- `LOAD FROM` reads external data without persisting it, and `COPY ... TO`
  exports results without modifying the database.

See [Data I/O](../data_io/index.md) for formats and usage.

## Durability and checkpoints

Applications do not need to run `CHECKPOINT` after ordinary committed writes.
NeuG records those commits and recovers them automatically after a normal
restart.

A manual checkpoint is optional maintenance that consolidates recovery state
and can reduce how much log data must be replayed during startup. Persistent
Embedded-mode bulk imports create the checkpoint they require before returning
success.

See [Checkpoints](checkpoint.md) for when to create one, failure behavior, and
configuration such as `checkpoint_on_close`.

## Failure behavior

- A failed auto-commit statement publishes no partial changes.
- A database-side failure inside an explicit transaction makes that transaction
  rollback-only. Roll it back before issuing another query.
- Client-side validation errors that occur before a query reaches NeuG do not
  change the transaction state.
- If a Service-mode connection fails while committing or rolling back, the
  outcome may be unknown. Close that session and create a new one rather than
  retrying blindly.

The complete rules are documented in
[Explicit Transactions](explicit_transactions.mdx).

## Recommended usage

- Prefer auto-commit unless several statements must form one unit of work.
- Keep explicit transactions short and always finish them with commit or
  rollback.
- Do not share one `Connection` or `Session` between concurrent client tasks.
- Use Embedded mode for file import/export, ETL, and analytical batch work.
- Use Service mode for concurrent application requests after data has been
  prepared.
- Let NeuG infer `access_mode`, or provide the narrowest correct mode when
  Service-mode concurrency matters.
